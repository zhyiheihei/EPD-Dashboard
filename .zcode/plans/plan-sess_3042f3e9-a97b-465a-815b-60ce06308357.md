# EPD-Dashboard 家庭食品存储看板系统 — 实施规划

## 一、勘探结论（决定架构的硬事实）

**目标机器 EPD-nRF5**（同级仓库，已实现"看板协议 v1"，固件 v0x1F）：
- nRF52811 + 7.5寸 800×480 UC8179 黑白红墨水屏；BLE 服务 UUID `62750001-d828-918d-fb46-b6c11c675aec`，广播名 `NRF_EPD_XXXX`，无配对加密，持续可连接
- **设备不接收文本**（印证"无法存储字库"）：服务端必须把食品名称渲染成 1-bit 位图（152×20=380字节，MSB-first，1=黑，≤1024字节）；图标/边框/日历/"剩余天数"由设备本地绘制
- 食品记录 6 字节：`slot + type(0=食品/1=饮品) + expiry_utc(4B)`；上限 **4 条食品、2 条日程**；服务端取**最近到期前 4 名**
- 流程：INIT → CAPS(校验 800×480/协议01) → BEGIN(UTC+时区+480+食品记录) → 逐资源 BITMAP 分片（保守 6 字节/片，Linux 可更大；每资源等 42 OK，末片带 CRC-16/CCITT-FALSE）→ COMMIT(0x03 刷新+休眠驱动)；全刷约 15 秒；失败需主动 ABORT 换事务 ID 重试
- 协议权威文档：`EPD-nRF5/docs/dashboard-protocol-v1.md`，参考实现 `EPD-nRF5/html/js/main.js`

**opi5p 服务器**（NixOS，192.168.0.62，常驻开机）：
- **PostgreSQL 18 已运行**，标准模式 `ensureDatabases/ensureUsers + ensureDBOwnership`（照抄 `nixos/optional-apps/bitmagnet.nix`）；规范要求新服务用自己的库、不碰别人的
- `hardware.bluetooth.enable = true`（BlueZ 就绪）；无防火墙，服务绑 127.0.0.1 走 nginx vhost（`lantian.localVhosts` + `accessibleBy="private"`）
- 0 点 timer 现成范例：`OnCalendar = "*-*-* 00:00:00"` + `Persistent = true`；服务加固 `LT.serviceHarden`（BLE 需放开 `PrivateDevices`）；强制 `Restart` 策略；secrets 走 sops-nix；部署 colmena

## 二、技术决策（推荐值，可随时改）

| 项 | 选择 | 理由 |
|---|---|---|
| 客户端 | **Tauri 2 + Vue 3 + Element Plus** | 当下最热门轻量桌面方案，中文生态最好，无边框+自绘标题栏成熟 |
| 服务端 | **Python 3.12：FastAPI + bleak + Pillow + psycopg** | bleak 是 Linux BlueZ 最成熟异步 BLE 库；Pillow 中文栅格化可靠；Nix 打包简单 |
| 数据库 | opi5p 现有 PostgreSQL，新库 `epd_dashboard` | 用户指定"用 opi5p 常用数据库" |
| 推送策略 | 每天 0 点（systemd timer）+ 数据变更防抖即时推送 | 0 点兜底 + 所见即所得 |
| 安全 | 客户端**只**与服务器 HTTPS 通信（Bearer Token）；只有服务端碰数据库和蓝牙 | 满足"客户端只对服务端连接" |

## 三、架构

```
┌────────────────┐  HTTPS + Token(内网)  ┌─────────────────────┐  BLE 看板协议v1   ┌───────────────┐
│ 客户端 (桌面)    │ ───────────────────→ │ 服务端 (opi5p)       │ ───────────────→ │ EPD-nRF5 墨水屏 │
│ Tauri2+Vue3    │  /api/foods CRUD     │ FastAPI + PostgreSQL │ 1bit位图+到期数据 │ 800×480 BWR   │
│ 无边框窗口      │  /api/epd/push       │ +bleak +Pillow渲染    │                 └───────────────┘
└────────────────┘                      └─────────────────────┘
```

## 四、数据模型（对齐协议）

```sql
CREATE TABLE foods (
  id SERIAL PRIMARY KEY,
  name VARCHAR(32) NOT NULL,            -- 食品名称（渲染为位图）
  category VARCHAR(32) NOT NULL,        -- 品类型（自由文本+预设：饮品/生鲜/乳制品/调味品/零食/主食…）
  production_date DATE NOT NULL,        -- 生产日期
  shelf_life_days INT NOT NULL,         -- 保质期（天，客户端负责年/月换算）
  quantity INT NOT NULL DEFAULT 1,      -- 数量
  created_at/updated_at TIMESTAMPTZ,
  consumed_at TIMESTAMPTZ NULL          -- 软删除（吃掉了/过期清理），不参与上屏
);
-- expiry_date = production_date + shelf_life_days（服务端计算）
-- 上屏选择：consumed_at IS NULL ORDER BY expiry_date ASC LIMIT 4
-- type 映射：category == '饮品' → 1，其余 → 0
```

## 五、分阶段实施

### 阶段 1：仓库骨架
```
EPD-Dashboard/
├── flake.nix                 # devShell + server/client 打包输出
├── server/                   # Python 服务端
│   ├── pyproject.toml
│   └── epd_food_server/
│       ├── main.py           # FastAPI 入口 + CLI（serve/push-now 子命令）
│       ├── config.py         # DSN/token/设备过滤/分片大小等
│       ├── db.py             # psycopg 连接池 + 启动自动建表迁移
│       ├── api/foods.py      # REST CRUD（Bearer token 中间件）
│       ├── api/epd.py        # push/status/health
│       ├── render.py         # Pillow：文本→152×20 1-bit 位图（超宽自动缩字号→省略号截断）
│       ├── protocol.py       # 看板协议 v1 帧构造（CAPS/BEGIN/BITMAP/COMMIT/ABORT/CRC16，纯函数可单测）
│       ├── ble.py            # bleak：扫描(UUID过滤)→连接→notify→事务流程→重试/ABORT
│       └── pusher.py         # 推送编排：top4 选择 + flock 锁防并发 + 失败记录
├── client/                   # Tauri 2 + Vue 3 + Element Plus
├── deploy/food-storage.nix   # NixOS 模块（见阶段 3）
├── tests/                    # 协议帧/渲染器/API 测试
└── docs/architecture.md
```

### 阶段 2：服务端
- REST API：`GET/POST /api/foods`、`PATCH/DELETE /api/foods/{id}`、`GET /api/foods/stats`、`POST /api/epd/push`（手动）、`GET /api/epd/status`（上次推送结果/设备名）、`GET /api/health`
- BLE 会话严格按协议：CAPS 校验（协议01、800×480）→ BEGIN（UTC+时区+480、食品记录）→ 6 个名称位图逐个发送等 OK → COMMIT(03)；默认保守 6 字节/片（配置可调大加速 Linux 推送）；60 秒超时；失败 ABORT + 指数退避重试 2 次
- 即时推送：写 API 触发后台防抖任务（10 秒合并连续修改），与 0 点 timer 用文件锁互斥
- 时区 Asia/Shanghai；服务绑定 127.0.0.1

### 阶段 3：NixOS 模块（deploy/food-storage.nix，迁入 nixos-config）
- `services.postgresql.ensureDatabases/ensureUsers`（epd_dashboard 库）
- 常驻 API 服务：`LT.serviceHarden` + `PrivateDevices=mkForce false`（蓝牙）+ `Restart=on-failure`（满足仓库策略）
- `systemd.timers.epd-food-push`：`OnCalendar = "*-*-* 00:00:00"` + `Persistent = true` → oneshot `ExecStart = epd-food-server push-now`
- nginx：`lantian.localVhosts` + `accessibleBy = "private"`，域名 `epd.opi5p.zhyi.xin`
- sops-nix secret：API Token（nixos-secrets 仓库新增 `common/epd-dashboard.yaml`）
- 端口登记 `helpers/constants/ports.nix`；在 `hosts/opi5p/configuration.nix` 加一行 import；`colmena apply --on opi5p` 部署（提供精确 patch 步骤，nixos-config 的改动会先征求确认）

### 阶段 4：客户端（无边框 UI）
- Tauri 2（`decorations: false`）+ Vue 3 + Vite + Element Plus + 自定义标题栏（拖拽区/最小化/最大化/关闭）
- 页面：① 仪表盘——临期 Top4 预览（模拟墨水屏观感）+ 库存/临期统计；② 食品管理——表格（名称/品类/生产日期/保质期/数量/剩余天数徽标：绿>7天、黄3-7天、红≤3天/已过期）、筛选排序、增改对话框（品类下拉+自由输入、保质期年/月/日单位切换）；③ 推送——手动推送按钮 + 上次推送状态；④ 设置——服务器地址/Token/主题
- 只依赖 axios→服务端，无 BLE/DB 代码

### 阶段 5：测试与联调
- 单测：protocol.py 帧字节对照 EPD-nRF5 参考 JS 实现逐字节验证；render.py 位图尺寸/打包/CRC；API 集成测试（临时 pg）
- 渲染效果先用 EPD-nRF5 自带 SDL2 模拟器/headless PPM 目检
- 真机清单：opi5p `bluetoothctl` 确认适配器→部署→客户端录入食品→手动推送→屏幕核对（vendor 内核 BLE 若有兼容问题，fallback 文档写明排查路径）

## 六、风险与对策
- **vendor 内核 BLE 角色兼容**：nanopi-r5c 已验证过 BLE central 可行；服务端是 central 角色（设备是广播方），实机验证步骤写入文档
- **设备重启丢位图**（协议明确 RAM-only）：0 点推送兜底 + 手动推送按钮；预留周期重推配置项
- **并发 BLE 会话**：文件锁互斥 timer 与 API 触发的推送
- **全刷 15 秒**：推送超时设 60 秒，客户端状态轮询提示"推送中"
